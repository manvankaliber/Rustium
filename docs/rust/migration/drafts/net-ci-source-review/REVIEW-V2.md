## Findings

1. **P1 — PR approval survives a changed head.** `.github/workflows/network-consumer-build.yml:4-5,31-35,42` triggers on `synchronize` and accepts the presence of `rustium-build-approved`, while selecting the event's current head SHA. A label remains on the PR after a push: a previously approved same-repository PR can therefore automatically run a new, unreviewed commit on the persistent host. `:102-103` applies the same persistent-label problem to the optional probe. The same-repository condition and GitHub external-contributor approval limit the exposure but do not tie review to this head. The full-SHA format check validates syntax, not approval. Use a trusted approval mechanism that records the exact head SHA and authorized actor and verifies that SHA immediately before execution, with a fresh approval after every head change; alternatively disable PR triggers and allow only an explicitly controlled, reviewed exact-SHA manual dispatch. Bind the probe decision to that same revision. Keep the workflow/control definition itself in a trusted revision. Recheck the final implementation and event behavior before enabling the runner.

2. **P1 — Native-window exclusion does not protect preparation or reliably detect competing work.** Workflow `:60-63,72-91` checks a fixed process-name list before checkout, fetch and dependency sync; `tools/ci/build_network_consumers.py:132-149` acquires its advisory lock only after preparation and has a different list. The driver's list omits `gn.exe`; both omit, for example, `cl.exe`, `link.exe`, `siso.exe`, and singular `*_perftest.exe`. Local Windows PowerShell 5.1 pattern checks confirm those names do not match and that `gn.exe` matches only the workflow guard. A pre-existing GN process can be missed by the later check, and a process can start between either snapshot and mutation. The Actions concurrency group serializes this workflow's jobs, and the lock excludes only participants using the same lock; neither excludes independent work. This can mutate source or dependencies while another native job is using them, violating the single validation window and invalidating evidence. Establish a shared, cooperative machine-wide reservation **before** any checkout/sync/hooks and hold it through the complete build and evidence finalization; require all authorized native work to honor it. Reconcile and stop only authorized conflicting work, add comprehensive process diagnostics as a secondary check, and verify handoff/race behavior on the laptop before launch. Do not rely on an ever-growing executable-name list as the lock.

3. **P1 — Recorded revisions do not establish the actual dependency and source bytes.** Workflow `:60-61,86-91` and driver `:141-143,176,210-222` ignore untracked top-level files and only compare top-level tracked status, `DEPS`, and before/after `gclient revinfo --actual` output. Git revisions do not detect modified or untracked files inside synced dependency repositories, nor untracked source files in the primary checkout. Such inputs can affect GN or compilation while `build_passed` is true for a nominal revision. The checks do detect tracked top-level drift, tool hashes, GN args and Ninja graph changes, and they record dependency revisions; those controls do not establish clean dependency bytes. Before any sync preserve and reconcile the dedicated checkout and every relevant nested dependency; require clean tracked and relevant untracked inputs or explicitly hash and account for all actual build inputs, then verify the same identities after the build. Preserve generated/output and approved tool-managed files under an explicit reviewed policy. Treat a dirty or unverifiable dependency as a failed qualification, not a successful build of the reviewed source.

4. **P2 — Failure evidence is incomplete before the build driver starts.** Workflow `:64-78,83-91,112-119` creates the evidence directory and exports its path only after several checks; a wrong host, dirty checkout, conflicting process, checkout-policy failure or existing evidence path exits before the upload condition can run. Failures in fetch/sync are at least eligible for transcript upload after the path is set, and the driver retains command logs and a false result for exceptions inside its guarded block (`build_network_consumers.py:116-126,224-233`); an error before its `try`, or hard process termination, may still lack `result.json`. Actions logs remain separate but this is not the documented uniform raw-result record for every run. Initialize a unique safe run record before fallible checks, record phase/outcome including preflight and dependency errors, and finalize/upload it on every possible exit; explicitly mark missing or interrupted final results as failed/incomplete. Never overwrite earlier evidence.
