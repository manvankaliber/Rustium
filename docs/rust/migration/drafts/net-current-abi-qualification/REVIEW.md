## Strings bridge and component boundary

The exact archived `string_split.cc` before-image is `84e1b041d22080a8d5f4ec8aa66e609fc673e1a0fdd75307e100811c0c210155`; the applied file is `8f22ae39602689cb738848f64ce7de09d70a6eb0358ef019d3e350c229934063`. The four `SplitStringOnce`/`RSplitStringOnce` overloads and four key/value APIs retain their C++ signatures and C++ return/output containers. `string_split.h` and `string_split_internal.h` retain the same hashes in the prior and current manifests; the other header-inline split APIs therefore are not newly routed by this change. The original helper implementations are replaced by synchronous typed CXX calls. Rust returns owned `Vec<Range>` metadata; C++ owns/destructs that bridge vector and reconstructs views into the caller's original input after bounds checks. Returned `std::string_view`s still borrow caller storage; they do not own Rust storage. Owned pairs are copied before return, and the original parse-before-clear ordering for owned output is retained. Empty missing fields use default views, while valid empty slices retain input identity where representable. Byte input is passed as a slice, including embedded NUL; the separate `u16` wire works in code units and is not itself a routed public UTF-16 API.

For the view-pair path, boundaries are collected before iteration, then each segment is parsed synchronously and appended before its diagnostic is emitted. This allows a diagnostic callback to mutate later input bytes without a Rust borrow surviving the callback, matching the relevant original ordering when caller storage remains valid. The authored bridge test exercises null/borrowed empty identity, embedded NUL, UTF-16 wire offsets, direction, and a non-reallocating callback mutation; source review is not evidence those tests passed at this identity. Reentrant destruction or mutation invalidating the input/output storage is not newly guaranteed: callers must preserve storage for the borrowed views and the active call. Allocation behavior, error/diagnostic equivalence, callback reentry, range invariants, and generated CXX ABI still need current build and runtime evidence; no authored `unsafe` is apparent in the reviewed glue, while generated CXX FFI is enabled as unsafe by the build target.

The graph binds `//base:string_split_rust` and its generated CXX target into `//base:base`; retained Ninja query lists `obj/base/base/string_split.obj`, `obj/base/string_split_rust_cxx_generated.lib`, and the Rust rlib in `base.dll` inputs. `//net:net` depends on `//base:base`, and the retained query lists `base.dll.lib` among `net.dll` inputs. `base_unittests.exe`, `base.dll`, `base.dll.lib`, `net.dll`, and `net.dll.lib` are already in 155. This is shared-component linkage, not an isolated Network-only bridge. GN also evaluates a system-allocator `//base:base` variant; this review does not claim that variant was built, nor require it solely because the unchanged header was included. Other base.dll consumers receive the new behavior at runtime; they are not thereby proven behaviorally compatible.
