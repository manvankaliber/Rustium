# Entire net stack migration worklist

This is a source inventory and execution plan, not a completion report. The authoritative component entries and per-file evidence live in `net-migration-status.json`. Refresh with `python tools/update_net_rust_migration_inventory.py`; update explicit component/file decisions and acceptance evidence in that JSON first. The updater preserves decisions, scans every file under net, captures hashes, lexical GN membership/dependencies, direct source include dependencies and existing configured Ninja membership. It does not run GN or Ninja. File counts measure inventory size, never module completion.

The scope includes all net subsystems, test and tool infrastructure, platform adapters and vendored sources. Dependencies outside net remain explicit project work; external does not mean rewritten or excluded from eventual migration. Existing filename utilities, HTTP chunked decoder and structured-header sfv wrappers predate this wave. Filename Rust currently delegates a conversion to C++; its existence does not establish a migrated algorithm. Structured-header container construction and feature policy still use C++. Other local Rust parser work also predates this inventory and needs its own acceptance evidence.

## Execution and ownership

Assign one bounded API family and its implementation/header/core/adapter/tests to each owner; never assign an entire large directory as one concurrent change. The JSON subsystem entries are routing groups, not implementation-sized assignments. Parent owns all shared GN, http_util.cc, configured-tree synchronization, Ninja, benchmark timings/gallery/aggregate and optimization backlog. Workers supply wrapper patches/GN fragments and freeze original C++ plus helper dependencies before mutation. The first wave is production-integrated and configured-validated on Windows x64: numeric + Content-Range, Content-Type/ParseMimeType, Content-Disposition, DNS name utilities, HTTP status mapping, Referrer-Policy parsing, auth challenges, diagnostic formatting and port policy. The optimized acceptance report and all remeasurements are archived under `docs/rust/benchmarks/`. Including earlier DataPack, gzip, HSTS and MIME sniffing work, there are 14 accepted feature slices. This is not a count of fully migrated subsystems; the JSON ledger records their remaining C++ seams.

The dependency order below describes core extraction followed by ownership integration. Runtime dependencies contain cycles: certificate revocation, PAC fetching and device-bound session refresh use URLRequest, which itself depends on HTTP/TLS/proxy. Break cycles with explicit narrow service interfaces and fake services in focused tests; retire those interfaces only when both sides migrate. Do not implement mutually recursive ownership ports concurrently without a parent-agreed interface contract. JSON dependencies give prerequisite subsystem relationships for final integration; parser slices may execute earlier as shown below.

## Acceptance ledger and next independent assignments

After parent lands and validates wave 1, assign these bounded slices first: DNS wire record parsing (keep resolver/service ownership separate), proxy bypass/rules (keep PAC services separate), cookie canonicalization/inclusion (keep persistent store separate), WebSocket frame/mask codec (keep HTTP handshake separate), and disk-cache index/key formats (keep async backend separate). Before assignment inspect the exact file/header dependencies and freeze helper closures; JSON include edges and GN source memberships provide the starting list. Avoid assigning whole http_util.cc: parent alone applies shared method patches. These slices can overlap in time with platform-interface research, but benchmark timing requires a coordinated quiet window.

For each slice track two independent axes: **logic** (C++, candidate Rust, parent-integrated Rust, configured validated) and **ownership/adapter** (C++ owner, documented ABI bridge, Rust owner, retired seam). A parser with a C++ caller is not a completed subsystem. Never promote a status automatically from a filename or a target entry. A validated status needs source manifest, exact configured build/test command/results, platform scope and acceptance evidence. Preserve historical results rather than overwriting them.

Each implementation owner supplies meaningful differential edge/alias/failure tests, deterministic fuzz runs, authored Rust region/line coverage with exclusions, rustfmt/Clippy and format results. Parent runs required canonical builds and tests. Test filters above describe families, not claims that an exact filter or target has executed. The JSON records actual lexical target labels and per-file test/perftest/fuzz sources so an owner can choose an executable target after evaluating platform conditions.

Performance is not a migration rejection criterion. Parent measures same-process paired original-C++ versus public Rust-backed API, preserving ownership/FFI/destruction costs, all cases and regressions. Include workload, source/binary hashes, toolchain flags, exclusions, repetitions and uncertainty. Record measured regressions in gallery and optimization backlog with exact evidence, affected seam, suspected versus verified cause and a concrete follow-up. Bridge retirement may help but cannot promise to remove an algorithmic regression. No benchmark was run for this inventory.

## Seam retirement and platform limits

- base: callbacks, task runners, refcounts, WeakPtr, clocks, files and event loops can retire only after owners and callers migrate; safe parser cores can use borrowed values meanwhile.
- url/ICU/PSL: preserve canonicalization, IDNA, charset and site behavior; changing public GURL ownership requires consumers outside net. Keep conversion policy distinct from byte parsing.
- crypto/BoringSSL: key ownership, TLS handles, certificate verification and primitive-provider interfaces remain explicit. Rust wrappers are interop until policy and ownership move. Platform credentials/trust APIs remain necessary system adapters even after Rust ownership.
- QUICHE: net/quic and net/spdy are Chromium integration; vendored protocol/HPACK/QPACK implementation is separately inventoried. Porting an integration wrapper does not port QUICHE.
- codecs/storage: gzip header Rust does not replace zlib, Brotli or Zstd; extras SQLite and protobuf-generated storage remain separate dependencies. Preserve format compatibility and recovery semantics.
- generated/test/vendor: inventory classifications describe purpose; tests and headers still require API updates and external sources remain in eventual project scope. Generated outputs should be changed via generator/schema, not hand-edited.

GN capture is lexical across conditional branches, not an evaluated dependency graph. Direct include edges are not a transitive semantic dependency proof. Conditional OS code, dynamically generated source lists and non-net embedder call sites need per-slice investigation.
